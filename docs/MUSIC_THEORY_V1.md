## Supported capabilities

| Area | Implemented v1 boundary |
| --- | --- |
| Pitch and notation | Numeric classes 0..11 with C=0; non-wrapping registered semitone coordinates with C0=0; explicitly spelled and registered notes; ASCII/Unicode note parsing/formatting; reverse spelling with a required sharps/flats policy. |
| Intervals | Explicit numbered, qualified up/down intervals; spelled and registered transposition, signed semitone measurement, spelled identification, formatting, and supported simple-interval inversion. Compound distance is preserved by registered operations. |
| Scales and modes | Existing major/minor collections, seven major-scale modes, pentatonics, numeric chromatic collection, fixed modes of harmonic/ascending melodic minor, and bounded registered runs. Melodic-minor traversal explicitly selects fixed-collection or classical-exercise behavior. |
| Degrees and keys | Collection ordinals versus major-relative formula roles; major/minor key identity, conventional signatures, relative/parallel keys, and explicit key-aware spelling. A chromatic class outside the signature baseline remains unresolved unless a matching role is supplied. |
| Chord content | Nonempty custom formulas with positive safe-integer role numbers and alterations through +/-3; 37 named qualities; selected-degree or full seven-note collection triad/seventh harmonization. Unnamed derived formulas remain representable. |
| Descriptions and symbols | Numeric/spelled root, ordered formula, optional specified bass; the [bounded symbol grammar](#chord-symbol-grammar) with documented aliases/canonical forms and slash bass. Custom formulas need not have symbols. |
| Registered chords | Explicit nonempty numeric/spelled voicings retaining supplied order and repeated tones; narrow root-position realization at an explicit matching registered root, preserving full compound-role distances. |
| Known-chord analysis | [D052](DECISIONS.md#d052-known-chord-bass-inversion-and-voicing-analysis) coverage, explicit required/optional omissions, doubling, bass, specified-bass agreement and spacing. Conventional inversion numbering covers only supported 1/3/5 and 1/3/5/7 structures, independently of sounding-note count. |
| Identification | [D053](DECISIONS.md#d053-exact-catalog-chord-identification) returns all exact complete pitch-class matches, preserving alternatives without ranking or selecting spelling. Registered inputs add observed bass evidence, not inversion status or specified-bass intent. |

These are portable modules under `domain/music-theory/`, imported directly using relative `.js` specifiers. They have no framework, rendering, audio, instrument or network prerequisites. Detailed entry points and representation-specific guarantees follow the handoff sections below.

## Information to retain at the Fretboard boundary

Music Theory determines musical content. The [implemented Fretboard v1](FRETBOARD_V1.md#operations-and-output-guarantees) maps target classes or registered pitches to identified strings/frets using explicit registered tuning and fret bounds. `findPitchClassLocations` searches across registers; `findRegisteredPitchLocations` preserves the exact target register. Both return `{ stringId, fret, pitch }` alternatives. Consumers retain the source objects below alongside those numeric results; no shared musical-request schema is introduced.

The [Fretboard v1 consumer guide](FRETBOARD_V1.md) continues this handoff with explicit physical string positions, strict search and numerical limits, and the information Playability consumers must preserve. Its [readiness review](../plans/fretboard-v1-readiness.md) records dated verification separately from the original Music Theory review.

| Mapping need | Existing data to retain | Meaning for the consumer |
| --- | --- | --- |
| Any octave of a target class | Numeric pitch classes plus original collection tonic, ordinal/formula roles and spellings where supplied | A class does not choose register, spelling or a simultaneous grip. Scales/melodies currently require note locations only. |
| Exact registered targets | `RegisteredPitchVoicing.pitches`, or `RegisteredNoteVoicing.notes` converted with `registeredPitchFromNote` | Keep every occurrence and its original index. C4 and C5 are distinct; two C4 occurrences still express multiplicity. Do not deduplicate a requested voicing. |
| Musical chord identity | Original chord description: root, complete ordered formula and supplied spelling | Roles 2/9, 4/11 and 6/13 may share pitch class but remain different roles. Retain formula positions when associating coverage/omission data. |
| Required bass | Description's optional unregistered `bass`; observed bass evidence from a supplied realization is separate | No specified bass means unspecified, not root position. A specified non-chord bass stays outside formula coverage. Any exact registered-bass requirement must also retain the original voicing/register. |
| Allowed omissions | The caller's `optionalFormulaIndices`, alongside the unchanged description/formula | Every unlisted position is required. Missing required tones must not become optional because locations or fingers are inconvenient. |
| Interpretation alternatives | Identification candidates together with the original notes/voicing | C6/Am7 and symmetric roots remain alternatives. Numeric identification does not replace the original spelling, register, multiplicity or creative intent. |

These data already exist in separate contracts; keep them together when relevant rather than projecting every request into a set of pitch classes. The same exact registered pitch can have multiple string/fret locations; Fretboard must retain those location identities. Availability of individual locations does not establish that the notes can sound simultaneously or that a fingering is playable. [Playability](PLAYABILITY_REFERENCE.md) evaluates proposed grips without silently changing the musical request.

## Composition rules and deliberate information loss

Numeric conversion discards spelling. Pitch-class conversion also discards register. D053 matching ignores duplicate occurrences; it returns complete named identities, not the supplied voicing. D052 coverage tests role membership using pitch class or exact spelling independently of octave. It reports doubling, but a positive coverage result does not prove that a requested registered multiset has been realized: an octave move or removed doubling can preserve coverage. A realization consumer must check original exact pitches and occurrences separately when requested. [Playability assessment](PLAYABILITY_V1.md#assessment-and-support) implements this through `exactVoicing` for supplied shapes.

Root-position construction is a specific convention: explicit matching root, an unaltered formula role 1, no below-root formula tone, and no incompatible specified bass. It preserves formula order rather than sorting. Cadd2 at C4 ends on D4, while Cadd9 ends on D5. Arbitrary supplied voicings need not follow that placement. Incompatible slash bass is rejected by this constructor; use an explicitly supplied voicing for analysis instead of expecting inversion generation.

Spelled analysis requires exact letter/accidental membership and exact specified-bass agreement; numeric analysis accepts enharmonic class equality. For example, A can match B-double-flat numerically but does not spell C diminished seventh's seventh. Consumers must choose the analysis representation deliberately.

`parseScaleType` returns a union including pentatonics. Narrow out those two types before passing a parsed value to seven-note harmonization; the narrower harmonization contract is intentional. Key identity is separate from selected minor collections: choosing harmonic minor does not change the natural-minor signature. Relative-mode operations return a new tonic; use it rather than the parent's tonic for subsequent degree queries or runs.

## Limits and deferred work

- Exact derived spellings are limited to accidentals -3..3. Numeric construction may succeed when spelled output cannot be represented. Symbols/descriptions do not eagerly validate all derived spellings; request the relevant resolver before promising spelled realization.
- Registered coordinates, displacements, written octaves and applicable intermediate bases obey existing safe-integer limits. A valid pair of endpoints can still have an unsupported distance. Scale runs require explicit direction, positive octave extent and endpoint inclusion, with at most 10,000 emitted notes; this is an allocation limit, not an instrument range.
- Input validation is capability-specific. Parsers validate their documented grammars; typed root/letter/accidental inputs are not a universal untrusted-data boundary. Malformed text uses existing `SyntaxError` contracts, while semantic/representation limits generally use `RangeError`. The capability-driven [error-classification TODO](STATUS.md#known-maintenance-and-verification-follow-ups) remains open; no structured-error system is introduced.
- Symbols cover the existing named formulas, not every possible spelling convention or custom formula. Harmonization covers triads/sevenths of supported seven-note collections, not arbitrary/pentatonic harmonization. Conventional key signatures exclude theoretical signatures requiring more than uniform single sharps/flats.
- Suspended, extended and other unsupported formula structures retain bass/membership analysis without conventional inversion numbering. Naming inversions of C9/C11/C13 remains an [open decision](ARCHITECTURE.md#open-architectural-questions); triad/seventh numbering does not automatically extend to them.
- Identification requires complete catalog pitch-class equality. Optional omissions in D052 do not authorize approximate identification, missing-root inference or invented non-chord slash-bass matches. Contextual ranking, harmonic function, Roman numerals and key detection are deferred.
- Exhaustive catalogs, automatic voicing generation, voice leading, progression recommendations, contextual respelling, rhythm, audio/MIDI, engraving, guitar-specific omissions, string selection and finger assignments remain outside v1. Playability owns bounded known-template search; ownership of general generation and further playability policies remains open.

## Pitch classes and spelled notes

`domain/music-theory/pitch-pitch-classes-and-spelling/pitch-class.ts` provides the first minimal Music Theory capability: `PitchClass` represents numeric classes `0..11`, and `transposePitchClass` transposes a typed pitch class by a signed safe-integer semitone offset, wrapping into `0..11`. Unsupported offsets throw `RangeError`. Reducing the offset before addition preserves precision at the safe-integer limits. The module has no imports or framework, Node API, or UI dependencies. `tests/pitch-class.test.ts` covers all twelve classes, octave equivalence, positive and negative wrapping, large offsets, and invalid offsets. The project's named origin is now C = 0; a numeric class still carries no spelling or register.

`domain/music-theory/pitch-pitch-classes-and-spelling/note-spelling.ts` exports `NoteLetter` (uppercase A through G), `Accidental` (-3 through 3 for triple flat through triple sharp), and readonly `NoteSpelling` with required `letter` and `accidental` fields. `pitchClassFromSpelling` maps natural letters to C=0, D=2, E=4, F=5, G=7, A=9, B=11 and reuses numeric transposition for the accidental. Conversion loses spelling information in its numeric result and does not mutate the input. The only dependency is the sibling pitch-class module. This is a typed-input contract, not validation of arbitrary JavaScript or external data. `tests/note-spelling.test.ts` checks all 49 supported spellings, enharmonic equivalence, wrapping, frozen inputs, composition with numeric transposition, and compile-time rejection of unsupported inputs. See [D020](DECISIONS.md#d020-c-based-pitch-classes-and-explicit-note-spelling).

## Registered pitch coordinates

`domain/music-theory/pitch-pitch-classes-and-spelling/registered-pitch.ts` exports numeric `RegisteredPitch` semitone coordinates with C0 = 0 and readonly `RegisteredNote` spellings with a required written `octave`. `registeredPitchFromNote` adds the signed accidental to the natural letter's registered coordinate without wrapping; B-sharp3 and C4 both produce 48. Conversion preserves the input but loses spelling in the result. `transposeRegisteredPitch` adds signed semitones without discarding octave distance. `pitchClassFromRegisteredPitch` discards register using existing pitch-class transposition. Each function validates its numeric inputs and results as safe integers and throws `RangeError` for invalid values or overflow. Note conversion also requires a safe twelve-semitone octave base; letter and accidental validity retains the typed-input contract. Negative coordinates and octaves are supported. The module depends only on sibling domain capabilities. `tests/registered-pitch.test.ts` covers note/register conversion, octave boundaries, enharmonics, transposition, extraction, frozen inputs, type contracts, and numeric limits. See [D021](DECISIONS.md#d021-registered-pitch-coordinates-with-c0-as-origin).

## Note text and spelling selection

Triple accidentals and degree alterations are supported under [D039](DECISIONS.md#d039-triple-accidentals-and-degree-alterations). G-double-sharp major retains F-triple-sharp as its seventh. Derived spellings beyond ±3 still throw `RangeError` without respelling; conventional signatures remain limited to single accidentals. See the [completed triple-accidental effort](../plans/triple-accidentals.md).

`domain/music-theory/pitch-pitch-classes-and-spelling/note-text.ts` provides `parseNoteSpelling`, `parseRegisteredNote`, `formatNoteSpelling`, and `formatRegisteredNote`. Parsing accepts uppercase A-G with an optional accidental token: #/♯, b/♭, ##/𝄪, bb/𝄫, ###/♯𝄪, bbb/♭𝄫, or ♮. ASCII triples use three signs; Unicode triples use a single sign followed by a double sign. It trims outer whitespace and rejects internal spaces, lowercase letters, x, mixed accidentals, reversed Unicode composites, mixed ASCII/Unicode tokens, repeated Unicode accidentals, and quadruples. Spelling parsing rejects octaves; registered parsing requires a signed decimal integer octave (ASCII +/- optional, leading zeroes accepted). Unicode formatting retains dedicated double signs and uses ♯𝄪/♭𝄫 for triples. Malformed syntax throws `SyntaxError`; numerical limits use existing registered-note validation and throw `RangeError`. Formatting preserves the supplied spelling and written octave, supports `AccidentalNotation` ascii/unicode with Unicode default, omits a natural token, and normalizes numeric octave text. Only registered formatting includes an octave.

`domain/music-theory/pitch-pitch-classes-and-spelling/spelling-selection.ts` provides `spellingFromPitchClass` and `noteFromRegisteredPitch` with a required `SpellingPolicy` sharps/flats. Both prefer natural spellings and single accidentals for other classes; they do not infer key context. Selection returns independent objects that convert back to the source numeric value. Registered selection uses exact portable BigInt intermediates and rejects coordinates whose selected spelling would violate the existing safe-octave-base contract, including the extreme lower registered-coordinate limit.

## Intervals and transposition

`domain/music-theory/intervals-and-transposition/spelled-transposition.ts` provides `transposeNoteSpelling` and `transposeRegisteredNote` using readonly `SpelledInterval` with required positive safe-integer `number`, `quality` (perfect/major/minor/augmented/diminished), and `direction` (up/down). Simple 1/4/5 families accept perfect quality; 2/3/6/7 accept major/minor; augmented/diminished apply to either family except diminished unison, which is rejected. Compound intervals retain their octave displacement for registered notes. Letter displacement and semitone displacement determine the result separately, distinguishing C up an augmented unison (C-sharp) from a minor second (D-flat). Exact BigInt intermediates preserve numerical boundaries; semitone displacements and resulting registered coordinates must remain safe. Incompatible interval qualities, diminished unisons, numerical overflow, unsafe octave bases, and results requiring accidentals outside -3..3 throw `RangeError` rather than silently respelling. Input objects are preserved. Unregistered output discards register. `validateSpelledInterval` shares the same interval rules with text parsing without imposing the limits of a particular source note or resulting spelling.

`domain/music-theory/intervals-and-transposition/interval-text.ts` exports `parseSpelledInterval(text: string): SpelledInterval`. Accepted forms are compact symbols P/M/m/A/d plus a decimal number (`m3 up`), full quality plus a named interval from unison through fifteenth (`minor third down`, with octave for number 8), or full quality plus a decimal number (`major 16 up`). Compact quality symbols are case-sensitive; full words and direction are case-insensitive. Direction up/down is required at the end. Outer whitespace is trimmed and whitespace between tokens is allowed. Decimal numbers may have leading zeroes, but no sign, fractional notation, or ordinal suffix. Malformed text throws `SyntaxError`; shared interval validation throws `RangeError` for incompatible quality/number, diminished unison, or unsafe numeric displacement. `tests/interval-text.test.ts` covers all supported names/qualities, case distinctions, both directions, syntax/semantic errors, large compound intervals, and interval-text-to-transposition integration. No dependency or existing transposition behavior is changed. See [D024](DECISIONS.md#d024-interval-text-syntax-with-required-direction).

`tests/note-text.test.ts`, `tests/spelling-selection.test.ts`, and `tests/spelled-transposition.test.ts` verify text grammar/errors, ASCII/Unicode round trips, all twelve classes under both selection policies, negative register, qualified intervals in both directions, compound intervals, numerical boundaries, type contracts, and a parse-transpose-format path. These modules import only other Music Theory capabilities. See [D022](DECISIONS.md#d022-note-text-and-explicit-reverse-spelling-policy) and [D023](DECISIONS.md#d023-spelled-transposition-by-qualified-intervals).

`domain/music-theory/pitch-pitch-classes-and-spelling/registered-pitch.ts` also exports `semitoneDistance(from, to)`, returning the signed safe-integer difference `to - from` without octave wrapping and normalizing equality to positive zero. Invalid coordinates and unsafe differences throw `RangeError`.

`domain/music-theory/intervals-and-transposition/spelled-transposition.ts` also exports `identifySpelledInterval(from, to)` for registered spelled notes. It derives inclusive interval number from written letter/octave positions and quality from sounding displacement, retaining compound distance. Different written positions determine up/down direction, including equal sounding pitches such as C-sharp4 to D-flat4 (diminished second/up); altered same-position unisons use sounding direction, so C4 to C-flat4 is augmented unison/down. Identical notes use perfect unison/up by project convention. Pairs requiring unsupported qualities, opposing written/sounding motion, or unsafe displacement throw `RangeError`; no silent respelling or model expansion occurs. Existing register validation applies and inputs are preserved. `tests/interval-measurement.test.ts` covers explicit simple/compound and reversed examples, enharmonic boundaries, exact transposition round trips, frozen inputs, type contracts, and invalid/numerical limits. See [D025](DECISIONS.md#d025-registered-interval-measurement-and-identification).

`domain/music-theory/intervals-and-transposition/spelled-transposition.ts` also exports `invertSimpleInterval(interval): SpelledInterval`. It accepts validated interval numbers 1 through 8, computes complementary number `9 - number`, maps perfect to perfect, major/minor to minor/major, and augmented/diminished to diminished/augmented, and flips direction to model octave displacement. It returns a new object without changing the input. Compound intervals and invalid inputs throw `RangeError`; augmented octaves also throw because their inverses are diminished unisons, excluded by the existing interval contract. `tests/interval-inversion.test.ts` verifies all 26 invertible number/quality combinations in both directions, double inversion, exact spelling/register behavior after octave displacement, frozen inputs, parsing integration, and explicit input/output limits. See [D026](DECISIONS.md#d026-simple-interval-inversion-by-octave-displacement).

`domain/music-theory/intervals-and-transposition/interval-text.ts` also exports `IntervalNotation` (compact/full) and `formatSpelledInterval(interval, notation = "compact")`. Formatting preserves number, quality, and direction, producing canonical compact symbols (`m3 up`) or lowercase full English notation (`minor third up`). Full notation reuses the parser's names for numbers 1–15 and decimal numbers beyond them (`major 16 up`). Both forms round-trip through `parseSpelledInterval`. Invalid intervals or unsupported notation throw `RangeError`. The same symbol/name tables serve parsing and formatting.

`domain/music-theory/intervals-and-transposition/spelled-transposition.ts` also exports `semitonesFromInterval(interval): number`, exposing the existing validated signed displacement independently of source-note spelling or register. Up is positive, down is negative, and zero displacement is positive zero. Compound octave distance and safe-integer limits are preserved through the existing exact arithmetic. Inputs remain unchanged. `tests/interval-text.test.ts` and `tests/spelled-transposition.test.ts` verify canonical output, round trips, both directions, zero displacements, source-note independence, frozen inputs, and validation/numerical limits. See [D027](DECISIONS.md#d027-interval-formatting-and-public-semitone-displacement).

## Scales and ordinal queries

`domain/music-theory/scales-and-modes/scales.ts` exports `ScaleType` for major, natural-minor, harmonic-minor, melodic-minor-ascending, major-pentatonic, minor-pentatonic, and ionian/dorian/phrygian/lydian/mixolydian/aeolian/locrian, plus ordinal `ScaleDegree` 1..7. `scalePitchClasses(tonic, type)` returns five or seven pitch classes in tonic-relative degree order, with no repeated octave. `scaleNoteSpellings(tonic, type)` spells each interval role from the supplied tonic: seven-note scales use successive letters, while pentatonic collections skip letters according to their intervals. Both share upward tonic-relative interval definitions and reuse existing semitone and spelled transposition; major/Ionian and natural minor/Aeolian share their respective patterns. Major pentatonic uses P1/M2/M3/P5/M6; minor pentatonic uses P1/m3/P4/P5/m7. Spelling retains the triple-accidental limit and rejects unsupported results with `RangeError` rather than respelling. Numeric construction does not inherit that spelling limit.

`pitchClassAtScaleDegree(tonic, type, degree)` retrieves an ordinal degree; `scaleDegreeOfPitchClass(tonic, type, pitchClass)` returns its ordinal degree or `undefined` for non-members. E-flat is degree 3 in C natural minor but degree 2 in C minor pentatonic; flat 3 describes its major-relative formula instead. G is degree 4 in C major pentatonic while its tonic-relative interval is a fifth. Function signatures and `ScaleDegree` remain unchanged; runtime validation rejects degrees 6/7 for pentatonic and retains them for seven-note scales. Unknown types and invalid degrees throw `RangeError`. Inputs retain the existing typed pitch/spelling contracts and remain unchanged; construction returns independent readonly arrays and independent note objects. `tests/scales.test.ts` and `tests/pentatonic-scales.test.ts` verify every numeric tonic/type, mode rotations, independent spelling expectations for all 49 tonic spellings, enharmonics, accidental limits, scale-specific degree queries, type contracts, and parse/construct/format integration. The fixed melodic-minor-ascending collection is distinct from the explicit convention-aware traversal described below. See [D028](DECISIONS.md#d028-seven-note-scales-modes-and-ordinal-degrees), its additive [pentatonic extension D029](DECISIONS.md#d029-pentatonic-collections-and-scale-specific-ordinal-limits), the [completed seven-note effort](../plans/scales-and-modes.md), and the [pentatonic effort](../plans/pentatonic-collections.md).

## Relative and minor-derived modes

`domain/music-theory/scales-and-modes/relative-modes.ts` exports `MajorScaleMode` (the seven canonical mode names), `RelativeModeParent` (those modes plus major/natural-minor aliases), and readonly `RelativePitchClassMode` / `RelativeSpelledMode` results. `relativeModePitchClasses(tonic, parent, degree)` returns `{ tonic, mode, pitchClasses }`; `relativeModeNoteSpellings(tonic, parent, degree)` returns `{ tonic, mode, noteSpellings }`. Each constructs the parent using the existing scale capability and rotates its seven members to the selected ordinal degree 1..7. C major degree 2 yields D Dorian; D Dorian degree 6 yields B Locrian. Output names are canonical, including Ionian/Aeolian for the parent aliases at degree 1. The derived tonic is the first collection member; spelled output preserves exact parent spellings and shares that first note object with its result's tonic. Calls return independent readonly results without mutating the supplied tonic. Unsupported parents/degrees and parent spellings beyond triple accidentals throw `RangeError`; harmonic/melodic minor, pentatonic, and custom parents are excluded. This derives a relative relationship rather than constructing a mode at an independently supplied tonic. `tests/relative-modes.test.ts` verifies all supported parents, numeric tonics/degrees, 49 tonic spellings per parent including rejection limits, canonical aliases, reverse relationships, result isolation, and type contracts. See [D030](DECISIONS.md#d030-relative-relationships-between-major-scale-modes).

`domain/music-theory/scales-and-modes/minor-modes.ts` exports `MinorModeParent` (harmonic-minor/melodic-minor-ascending), readonly `MinorMode` with parent and rotation degree 1..7, direct `minorModePitchClasses` / `minorModeNoteSpellings`, relative `relativeMinorModePitchClasses` / `relativeMinorModeNoteSpellings`, and registered `minorModeRegisteredPitches` / `minorModeRegisteredNotes`. Direct construction derives upward interval roles from a fixed C parent using existing scale spelling and interval identification, then transposes from the supplied mode tonic. Relative derivation rotates the supplied parent collection and returns `{ tonic, mode, pitchClasses }` or `{ tonic, mode, noteSpellings }`, preserving exact spelling; the spelled tonic shares its first collection object. Results are independent readonly arrays/objects, not runtime-frozen. Unsupported parents/degrees and unrepresentable output throw `RangeError`. Numeric/spelled inputs retain existing typed boundaries. Registered modes use existing `ScaleRunOptions` and shared `scale-run-internals.ts` arithmetic: allocation cap, signed positioning, safe emitted pitches, and exact written-octave recovery. Named scale runs delegate to the same internals while retaining their public options/cap exports and behavior. Internals consume trusted domain-generated collections and do not establish a custom-pattern API. All fourteen derived modes remain fixed in both directions; D034 classical substitution applies only to its separate melodic-minor traversal helpers. `ScaleType`, major-mode contracts/names, degree queries, and text parsers remain unchanged. `tests/minor-modes.test.ts` verifies independent offsets/closing steps, all twelve numeric tonics, all 49 direct/relative tonic spellings, direct/relative agreement, both registered directions, numerical/spelling/allocation limits, input isolation, and type contracts. See [D035](DECISIONS.md#d035-fixed-modes-of-harmonic-and-ascending-melodic-minor) and the [mode effort](../plans/minor-derived-modes.md).

## Registered runs and melodic-minor conventions

`domain/music-theory/scales-and-modes/scale-runs.ts` exports `ScaleRunOptions` with required `direction` (up/down), positive safe-integer `octaves`, and boolean `includeEndpoint`, plus `MAX_SCALE_RUN_NOTES = 10_000`. `scaleRegisteredPitches(tonic, type, options)` returns readonly registered coordinates; `scaleRegisteredNotes(tonic, type, options)` returns readonly registered spellings. Both support every existing `ScaleType`, always include the starting tonic, retain internal octave tonics, and optionally include the final tonic exactly the requested octave distance away. The result has scale cardinality times octaves plus one when the endpoint is included. Reusing scale construction and registered transposition preserves each fixed collection in either direction; descending `melodic-minor-ascending` does not select classical/jazz traversal behavior. Spelled output preserves degree spelling and calculates written octaves with exact arithmetic, including B-sharp/C-flat boundaries. Independent arrays/notes preserve inputs and are readonly by type, not runtime-frozen. Unsupported types/options, excessive output size, unsafe emitted coordinates, unsupported accidentals, and unsafe written octave bases throw `RangeError`; an omitted final tonic is not calculated or validated. The note cap is checked before output allocation and never truncates results. `tests/scale-runs.test.ts` covers all types, both directions, octave/endpoints, all 49 tonic spellings per type, negative registers, output-cap boundaries, arithmetic limits, and type/input-isolation contracts. See [D031](DECISIONS.md#d031-registered-scale-runs-with-explicit-octave-extent) and the [run effort](../plans/registered-scale-runs.md).

`domain/music-theory/scales-and-modes/melodic-minor-runs.ts` exports `MelodicMinorConvention` (fixed-collection/classical-exercise), readonly `MelodicMinorRunOptions` extending `ScaleRunOptions` with required `convention`, and `melodicMinorRegisteredPitches(tonic, options)` / `melodicMinorRegisteredNotes(tonic, options)`. Both conventions ascend using melodic-minor-ascending; fixed-collection also descends using that collection, while classical-exercise descends using natural-minor. ## Chord-symbol grammar

`domain/music-theory/chords-symbols-and-realization/chord-symbols.ts` exports `parseChordSymbol(text: string): SpelledChordDescription` and `formatChordSymbol(description: SpelledChordDescription, notation: AccidentalNotation = "unicode"): string`. Private exhaustive family suffix tables reference existing catalog formula getters; parser aliases point to canonical entries and formatting uses the same entries. No musical formulas are duplicated in the notation layer, and existing construction, description and harmonization APIs remain unchanged. See [D050](DECISIONS.md#d050-bounded-chord-symbol-grammar-and-canonical-formatting) and the [effort](../plans/chord-symbols.md).

The grammar is root + complete suffix, optionally followed by /bass. Root/bass use uppercase A-G and the existing note accidental tokens: #/b, ##/bb, ###/bbb, ♯/♭, 𝄪/𝄫, ♯𝄪/♭𝄫, or ♮, with no octave. Omitted accidental means natural. Trim outer whitespace and reject all internal whitespace. Suffixes are case-sensitive; the following table lists the complete canonical ASCII vocabulary. Unicode output replaces suffix accidental signs with ♭/♯; parsing accepts either form independently of root/bass notation.

| Quality | Canonical suffix |
| --- | --- |
| major | empty |
| minor | `m` |
| diminished | `dim` |
| augmented | `aug` |
| sus2 | `sus2` |
| sus4 | `sus4` |
| major-seventh | `maj7` |
| dominant-seventh | `7` |
| minor-seventh | `m7` |
| half-diminished-seventh | `m7(b5)` |
| diminished-seventh | `dim7` |
| minor-major-seventh | `m(maj7)` |
| augmented-major-seventh | `aug(maj7)` |
| augmented-seventh | `aug7` |
| dominant-seventh-sus2 | `7sus2` |
| dominant-seventh-sus4 | `7sus4` |
| major-add2 | `add2` |
| major-add9 | `add9` |
| minor-add9 | `madd9` |
| major-add11 | `add11` |
| major-sixth | `6` |
| minor-sixth | `m6` |
| major-sixth-ninth | `6/9` |
| dominant-ninth | `9` |
| major-ninth | `maj9` |
| minor-ninth | `m9` |
| dominant-eleventh | `11` |
| major-eleventh | `maj11` |
| minor-eleventh | `m11` |
| dominant-thirteenth | `13` |
| major-thirteenth | `maj13` |
| minor-thirteenth | `m13` |
| dominant-flat-ninth | `7(b9)` |
| dominant-sharp-ninth | `7(#9)` |

Only additional aliases are `sus` → `sus4`, `7sus` → `7sus4`, `°` → `dim`, `°7` → `dim7`, `ø7` → `m7(b5)`, and `7(#5)` → `aug7` (also `7(♯5)`). All other suffixes, arbitrary alteration combinations, polychords, omissions and Roman numerals are unsupported. In particular, min, -, +, M7, Δ7, unparenthesized alterations and 7(#11) are outside this grammar. These are parser conventions, not claims that other notation is musically invalid; the reference's broader examples do not expand this vocabulary.

A terminal slash introduces bass only when the entire remainder is a supported note spelling. Thus `C6/9` has no bass, `C6/9/E` is a sixth-ninth chord with E bass, `C6/E` is a sixth chord with E bass, and `C/E` is a major triad with E bass. Root, chord-tone and non-chord basses are allowed. Preserve spelling and explicit bass, including `/C` on C; absence means unspecified. Digits are recognized suffix components, not octave text: C6 is a sixth chord, while C4 and C/E4 are rejected. Malformed or unsupported whole symbols throw `SyntaxError`, without partial parsing.

Formatting validates the formula and matches ordered numbers and alterations exactly, preserving the distinction between add2/add9. It does not sort, deduplicate, reduce compound roles or match merely enharmonic pitch classes. Malformed or unmatched formulas and invalid notation selections throw `RangeError`. Preserve root/bass letter and accidental, normalize explicit natural tokens away, emit canonical suffixes and append specified bass. Numeric-only descriptions require an external explicit spelling choice. Parsing creates copied, independent, unfrozen readonly-by-type descriptions; formatting does not mutate inputs. Neither operation resolves derived tones: G###maj7 can be parsed/formatted even though later spelled tone resolution requires an unsupported accidental. This layer adds no register, inversion, voicing, fingering, UI or AI behavior. `tests/chord-symbols.test.ts` verifies independent role fixtures, all roots/both notations, all bass spellings with representative symbols, aliases, slash distinctions, round trips, unsupported syntax/formulas, input/output isolation and type boundaries.

Both validate supplied voicings even when factories were bypassed. `ChordVoicingAnalysisOptions.optionalFormulaIndices` lists distinct zero-based optional positions; all remaining roles are required. Invalid options/indices, malformed formulas/voicings and unsafe distances throw `RangeError`; musical mismatches return evidence.

`RegisteredPitchVoicingAnalysis` and `RegisteredNoteVoicingAnalysis` share `ChordVoicingAnalysis`: `bass` holds minimum sounding `pitch`, `pitchClass`, every tied `toneIndices`, matching `formulaIndices` and unmatched bass indices. `specifiedBass` is unspecified/matched/mismatched; matching requires every lowest occurrence to agree, using pitch class numerically and exact spelling for notes. `coverage` preserves each formula index, copied role, required flag and matching tone indices. `missingRequiredFormulaIndices` and `missingOptionalFormulaIndices` distinguish omissions. Equivalent, repeated and enharmonic roles may share matching evidence without allocating separate note occurrences. Compound roles retain their identity without requiring a particular octave placement.

`unmatchedToneIndices` lists all tones outside the formula. `allowedSpecifiedBassToneIndices` contains only unmatched lowest occurrences agreeing with the specified bass; `unexpectedToneIndices` excludes those permitted occurrences but still includes upper non-chord repetitions. No bass is appended to the formula. `doublings` reports every repeated supplied identity, including non-chord identities, in first-occurrence order with pitch class, count and original indices; spelled results also contain a copied exact `spelling`. Bass/spacing indices recover supplied notes without selecting an enharmonic spelling.

`inversion` is a discriminated result: classified with root-position/first-inversion/second-inversion/third-inversion, or unsupported-structure/non-chord-bass/ambiguous. Supported formulas contain exactly one unaltered role 1 and one each of 3/5, optionally 7, in any order and without a catalog-name requirement. Altered tertian roles remain explicit. Suspended, duplicate-role, compound-substitution and other formulas outside these supported patterns are unsupported for conventional labels but retain all other analysis. Extended tertian chords such as C9, C11 and C13 also receive bass and chord-tone membership analysis without conventional inversion numbering; their naming conventions are deferred under [Open architectural questions](ARCHITECTURE.md#open-architectural-questions). After checking structure, no matching bass role means non-chord bass (for example F-sharp in C/F-sharp), not a conventional inversion; multiple matching roles or partly unmatched tied bass means ambiguous. A uniquely matching bass role determines inversion independently of omissions and unexpected upper tones. The formula has exactly three or four roles, but the voicing may contain any number of sounding notes: doublings, including voicings with four or more notes, do not change the inversion determined by the lowest sounding registered pitch and its role.

`spacing` returns stable ascending original `toneIndices`, total semitone `span` and `adjacentGaps`, retaining exact repetitions and zero gaps. A singleton has zero span and no gaps. Safe endpoints can still produce an unsafe span, which rejects through existing registered-distance validation. All outputs are independent, readonly by type and unfrozen. Analysis uses only existing portable domain modules; construction and realization do not depend on analysis. There is no identification, voicing generation, automatic omission policy, close/open label, fingering or ergonomic verdict. See [D052](DECISIONS.md#d052-known-chord-bass-inversion-and-voicing-analysis), the [analysis effort](../plans/chord-voicing-analysis.md), and `tests/chord-voicing-analysis.test.ts`.

## Exact chord identification

`domain/music-theory/chords-symbols-and-realization/chord-identification.ts` exports `identifyChordsFromPitchClasses(pitchClasses)` and `identifyChordsFromNoteSpellings(notes)`, returning readonly `ChordIdentificationCandidate` arrays. Each candidate contains a numeric `description` (root/formula, without specified bass) and a discriminated `family`/`quality` pairing: triad/`TriadQuality`, seventh/`SeventhChordQuality`, added-tone/`AddedToneChordQuality`, or extended/`ExtendedChordQuality`. Private exhaustive identifier tables reference the existing formula getters, precomputing twelve-bit pitch-class masks for all 37 qualities at twelve roots. No musical formulas or symbol suffixes are duplicated, and no public catalog registry is added.

Matching requires equality of complete pitch-class sets, ignoring supplied order, duplicate occurrences, spelling and octave placement. Return every root/quality alternative rather than collapsing equal sets: C-E-G-A retains C6/Am7, C-D-E-G retains Cadd2/Cadd9, and symmetric augmented triads and diminished sevenths retain all matching roots. Enumeration is root ascending, then family triad/seventh/added-tone/extended, then quality identifier alphabetically; order is not ranking. Spelled input does not filter by exact notation or choose root spellings. Candidates are numeric even if input was spelled; callers must explicitly select spelling before using existing symbol formatting.

`identifyChordsFromRegisteredPitches(voicing)` and `identifyChordsFromRegisteredNotes(voicing)` accept the existing numeric/spelled voicing records and return `RegisteredChordIdentification` with `bass` and `candidates`. Bass contains the minimum sounding `pitch`, its `pitchClass`, and every tied original `toneIndices`. Each `RegisteredChordIdentificationCandidate` adds `bassFormulaIndices` for every matching formula position. Observed bass never becomes specified-bass intent and never filters or ranks candidates. Bass evidence is returned even with no matches. Coordinate comparisons avoid spacing arithmetic, so safe endpoints remain supported when their total distance would be unsafe. No inversion status is attached; numeric known-chord analysis can be called separately, retaining D052's limits and the open extended-inversion naming question.

Empty/non-array collections, sparse/missing entries, and numeric classes outside integer 0..11 throw `RangeError`. Spelled letter/accidental fields retain typed boundaries; registered adapters reuse existing voicing factories and coordinate/octave validation, including direct records that bypassed factories. Valid no-match inputs return empty candidate arrays. Results and nested descriptions/formulas are independently copied, readonly by type and unfrozen. No optional omissions, inferred missing roots, approximate matches, contextual ranking, custom-catalog identification, automatic spelling or inferred non-chord slash bass is introduced. Existing constructors, symbols, descriptions, realization and D052 analysis APIs remain unchanged. See [D053](DECISIONS.md#d053-exact-catalog-chord-identification), the [identification effort](../plans/chord-identification.md), and `tests/chord-identification.test.ts` for independent catalog/all-root fixtures, ambiguity, adapters, validation, numeric extremes, ownership and integration checks.
